Overview

Three lines of Python. Any filesystem.

Anscom is designed for zero-configuration usage. Point it at any path — relative or absolute — and it handles everything: spawning worker threads, issuing OS syscalls, categorizing results, and returning a clean Python dict.

Unlike os.walk or pathlib.rglob, Anscom runs entirely in C with direct kernel-level syscalls. Memory usage is bounded regardless of filesystem size — scanning 50 million files uses no more memory than scanning 50,000.

API Reference

anscom.scan()

The entire public API is a single function. All parameters have sensible defaults — only path is required.

ParameterTypeDefaultDescription
pathstrrequiredTarget directory. Relative (.) or absolute (/data). Empty string treated as .

workersint0Thread count. 0 = OS core count. Overridden to 1 when show_tree=True.

Tree Output

DFS-ordered filesystem topology

When show_tree=True, workers is forced to 1 for strict depth-first traversal. Each line is written immediately via PySys_WriteStdout — no buffer accumulates. A filesystem with 4 million files produces 4 million lines without memory pressure.

The DFS guarantee means output is always topologically valid: every file appears after its parent directory and before the next sibling. This holds at any scale.

Report Format

Two tables, zero configuration

When silent=False (default), Anscom prints a Summary Report and a Detailed Extension Breakdown on completion. Both tables route through PySys_WriteStdout — redirect sys.stdout before calling scan() to capture them.

Architecture

Engineering decisions that matter

Six choices determine correctness and throughput. Each eliminates a specific bottleneck in naive Python filesystem traversal.

⚙
Direct OS syscalls
getdents64 on Linux, FindFirstFileW on Windows, readdir on macOS. No libc wrappers, no Python os module overhead.
⟳
Multi-threaded worker pool
N threads auto-detected from CPU core count. All threads running before the first directory is opened. Shared 131,072-slot circular queue.
▣
Slab path allocator
Each thread allocates one contiguous block before scanning begins. Zero heap allocation during traversal regardless of filesystem size.
≡
Per-thread statistics
No shared counters during file counting. Each thread writes only to its own ScanStats struct. Results merged in one serial pass after all threads join.
◈
Bounded memory at any scale
Memory capped by queue and path slabs — neither grows with filesystem size. Scanning 50M files uses no more memory than scanning 50K.
↺
GIL released for full scan
Worker threads operate under Py_BEGIN_ALLOW_THREADS for their entire lifetime. GIL re-acquired only for progress callback and final dict construction.
